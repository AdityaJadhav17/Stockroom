# Stockroom v1.0.0 release notes (draft)

Status: draft. The owner has not tagged or published this release. Sign-off, a hosted CI run on the M9 changes, the narrated demo, and the `main` ruleset remain open; see [Before publishing](#before-publishing).

Stockroom tracks supplies for a fictional campus makerspace. Members request purchases; a manager approves them, records deliveries, issues stock, and reads an audit trail of every change. All data is synthetic, and the application runs locally against SQLite.

## Capabilities

| Area | What the release does |
| --- | --- |
| Accounts | Three seeded accounts (two members, one manager) with ASP.NET Core Identity login and logout. No registration or password recovery. |
| Inventory | Ten items with name search, units, quantities, and reorder thresholds. Items at or below their threshold show as Low. |
| Purchase requests | Members request one item with a whole-number quantity and a reason. The manager approves or rejects with a reason; approval leaves stock unchanged. |
| Receipt | The manager records the full approved quantity once. A repeated or competing receipt adds stock only once. |
| Stock issues | The manager issues stock with a reason. An issue larger than the stock on hand is refused, including when two issues compete. |
| History | Request events and stock movements record the actor, UTC time, quantity change, reason, and request. Members see events on their own requests only. |
| Demo data | A Development-only `seed` command creates the dataset, reruns without changing existing records, and `seed --reset` rebuilds it. |
| Interface | Razor Pages with labelled status badges, phone layouts, light and dark themes, and keyboard access. |

## Security behavior

- The server checks every permission against the roles stored in the database, on each request and again inside the services.
- Logout rotates the account's security stamp, which ends every session for that account, including copied cookies.
- Login allows five attempts per client address per one-minute sliding window; the account locks after 11 failures.
- Every response sends a strict Content-Security-Policy, `X-Frame-Options: DENY`, `nosniff`, and a same-origin referrer policy.
- Database failures show a generic page; details go to the server log only.

## Limitations

- The application targets a local demonstration: no hosting configuration, HTTPS redirection, or HSTS.
- History and request lists have no paging, and members have no limit on open requests.
- `seed --reset` deletes the database before reseeding; if seeding then failed, the database would stay empty until the next reset.
- One client can lock an account after about 100 seconds of failed logins, and clients behind one address share the login limit.
- An active session renews without an absolute time limit.
- The unit-test project contains no tests; the integration tests cover the input rules.
- Item administration, multi-item orders, partial receipts, cancellations, stock corrections, suppliers, and email are outside the release.
