# Writing guide

The owner supplied the Stop Slop writing guidance and examples. Contributors use the rules below for README text, documentation, review notes, and handoffs.

## Editorial rules

- Lead with the purpose or result. Name the user, action, and consequence.
- Use active voice and concrete language. Prefer `The manager approves the request` to `The request is processed`.
- Cut filler, business jargon, intensifiers, and adverbs that add no meaning.
- Avoid em dashes, rhetorical questions, dramatic fragments, and formulaic contrasts.
- Vary sentence length. Use tables for requirements, responsibilities, and test cases.
- Explain technical details that affect setup, behavior, or review. Omit promotional claims and decorative badges.
- Label proposed behavior, implementation status, and verified results. Keep synthetic examples distinct from customer evidence.
- Preserve technical terms, API names, and precise requirements even if a general prose rule would shorten them.

## Review procedure

Read the draft for factual accuracy, then remove unnecessary words. Check for passive constructions, repeated sentence patterns, and vague claims. Confirm that links resolve and that status statements match the repository.

The owner requested professional project documents. Use headings and acceptance-criteria lists where they help a contributor find a requirement. Do not turn the supplied skill's installation instructions or examples into product requirements.
